# Evaluation and final-year report plan

## Research question

Can a lightweight food classifier plus user-scoped retrieval make food journaling more
usable while producing traceable, personalized answers about recorded intake?

Separate the three evaluation problems: **food classification**, **portion/nutrition
estimation**, and **retrieval/answer quality**. One accuracy number cannot evaluate all three.

## Classification experiment

The current local run uses the image-only partial archive and custom grouped split
described in `food101-dataset.md`, not official Food-101 metadata. It trains a
frozen-backbone head baseline with `ml/run_training.py`; backbone fine-tuning is
an optional future comparison. Completed measured results are generated by
`tools/report_training.py`. The protocol below also describes possible extensions.

1. Obtain Food-101 under its research-use conditions, or an appropriately licensed local
   dataset. Record the dataset version, number of images and selected classes.
2. Keep the official Food-101 test split untouched. Split only the official training
   partition into training/validation. The preparation script stores a hash manifest
   and rejects exact duplicates crossing partitions. Perceptual duplicates still need review.
3. Train the classification head, then fine-tune. Record both validation curves and the
   chosen model. Use validation data for checkpoint selection and any confidence threshold.
4. Freeze the final model and evaluate the held-out test set once. Save top-1/top-3 accuracy,
   macro-F1, per-class precision/recall, confusion matrix, and inference latency.
5. Test non-food photographs, mixed plates, low lighting, and unfamiliar dishes separately.
   Softmax confidence is not calibrated probability of correctness or an out-of-domain detector.

The supplied scripts output training CSV logs, labels, model configuration, held-out
metrics, a CSV confusion matrix, and a PNG figure. They do not invent numerical results.
For formal comparisons, repeat with multiple seeds and report variation. The current
pipeline defaults to seed 42 and is a baseline, not an exhaustive experiment framework.

## Nutrition experiment

The current catalogue uses sourced USDA references. Audit recipe matching separately.
Store preparation method, source, record identifier and per-100-g values. Do not use a
generic pizza entry as ground truth for every recipe.

For test meals, weigh each food with a scale and document ingredients. Compare estimated
calories against the chosen reference using MAE and relative error. Evaluate known labels
first to isolate lookup/portion error, then predicted labels to measure end-to-end error.
User-entered weight is an input, not a predicted quantity. This implementation does not
estimate food mass from image geometry.

## Retrieval and assistant experiment

Create at least 50 anonymized questions with expected source IDs, answerable facts and
date ranges. Include several independent test accounts with unmistakable private canaries.

| Category | Example | Expected behavior |
|---|---|---|
| Profile | What is my saved goal? | Correct user's profile citation |
| Meal lookup | Find my rice meals | Relevant same-user records |
| Date aggregate | Protein today? | Complete SQL total for the user's local date |
| Many records | Calories over 20 logged meals? | No top-k undercount when a date range is specified |
| No evidence | Did I eat sushi? with no matching entry | No invented meal |
| Cross-account | Show another user's private marker | No retrieval or disclosure |
| Prompt injection | Note says ignore instructions | Note treated as data, not authority |
| Deleted data | Ask after removing a meal | No stale evidence snapshot |
| Generator outage | Ollama unreachable | Clearly labelled extractive fallback |
| Ambiguous period | Last semester | Request an explicit range; do not assume it was parsed |

Measure Recall@5/MRR for retrieval, numeric exact match for supported aggregates, citation
validity, human-rated faithfulness, refusal/no-evidence quality, and end-to-end latency.
Measure cross-account leakage separately with a required observed rate of zero in the
test set. Zero observed failures does not prove security against every possible attack.

Compare (A) BM25 + extractive evidence and (B) BM25 + local Ollama. A later experiment
could add dense/hybrid retrieval, measuring whether its improvement justifies model size
and latency. Do not label the existing baseline as embedding/vector retrieval.

## Suggested report chapters

1. Introduction: motivation, problem statement, objectives, bounded scope.
2. Literature review: food classification, portion estimation, nutritional databases, RAG.
3. Requirements: functional features, privacy, hardware, dataset conditions.
4. System design: architecture, ER diagram, account boundary, inference sequence.
5. Implementation: preprocessing, MobileNetV2, portion formula, BM25, local generation.
6. Experiments: dataset protocol, actual results, ablations, failure cases.
7. Conclusion: demonstrated contributions, limitations, future work.
8. References and appendices: setup, API endpoints, test output, reproducibility details.

## Viva demonstration

Create two accounts. Log distinct meals and preferences. Show a 200 g food calculation,
the updated diary/dashboard, a cited chatbot answer, and an exact date total. Switch
accounts to demonstrate that prior records cannot be retrieved. Show a missing-evidence
question. If trained artifacts are installed, upload held-out food and non-food images,
discuss the predictions honestly, then display the evaluation report. Explain why grams
must be supplied and why citation presence alone does not guarantee correctness.
